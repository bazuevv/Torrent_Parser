# Правила работы в этом репозитории

## Контрольные точки (обязательно)

После КАЖДОЙ фазы из плана (каждая галочка верхнего уровня в твоём
todo-списке) ты обязан:

1. ОСТАНОВИТЬСЯ. Не переходи к следующей фазе автоматически.
2. Сделать git commit с изменениями этой фазы. Коммит только на файлы,
   относящиеся к этой фазе — `git add <конкретные пути>`, не `git add .`
   и не `git add -A`.
3. Формат сообщения коммита:

        Этап <N>, фаза <M.K>: <краткое описание>

   Пример: «Этап 1, фаза 2.3: декомпозиция includes/admin/sub/»
4. Показать мне:
   - какие файлы попали в коммит (`git diff --stat HEAD~1`),
   - что планируется в следующей фазе (1–2 строки),
   - явный вопрос: «Продолжать?»
5. Жди моего ответа. «ок», «да», «продолжай» — значит идти дальше
   (к следующей фазе; после её завершения снова остановиться и спросить).
   Ответ «даа» (с удвоенной «а») — значит идти до конца плана без
   дальнейших запросов подтверждений: ты всё равно коммитишь каждую
   фазу отдельно и ведёшь TodoWrite, но между фазами не останавливаешься
   и не задаёшь вопрос «Продолжать?». Действует до конца текущего плана
   (пока все todo не станут `completed` или план не будет отменён).
   Любой другой ответ — это корректировка, применяй её до следующего
   коммита.

Не объединяй несколько фаз в один коммит, даже если они прошли подряд
без правок. История должна отражать план: одна фаза — один коммит.

Если фаза развалилась на подфазы в процессе работы — коммить каждую
подфазу отдельно по тому же правилу.

## Дисциплина TodoWrite

В любой момент в todo-списке МОЖЕТ БЫТЬ РОВНО ОДНА задача со статусом
`in_progress`. Никогда не помечай две (и более) фазы как активные
одновременно — это ломает правило «Контрольные точки»: становится
непонятно, какую фазу коммитить и на каком шаге запрашивать подтверждение.

Правила переключения:
1. Начинаешь фазу → ставишь её в `in_progress`. Все остальные незавершённые
   фазы должны быть в `pending`.
2. Закончил фазу → сперва коммит по правилу «Контрольные точки», потом
   помечаешь её `completed`, потом ставишь следующую в `in_progress` —
   только после ответа пользователя «да/продолжай».
3. Никогда не помечай фазу `in_progress` авансом, даже если знаешь, что
   дойдёшь до неё следом. До подтверждения она остаётся `pending`.
4. Если обнаружил, что две задачи оказались `in_progress` одновременно —
   ОСТАНОВИСЬ, сообщи об этом пользователю и жди инструкций. Не пытайся
   «доделать обе» — это значит, что состояние рассинхронизировано.

Одна фаза `in_progress` → один коммит → один вопрос «Продолжать?».

## Bypass-режим (слово `да!`)

Слово **`да!`** (именно с восклицательным знаком) в сообщении пользователя
активирует bypass-режим для **tool-промптов harness** до конца сессии.
Это реализовано хуком `.claude/hooks/bypass-magic-word.py`, который ставит
marker-файл `.claude/hooks-runtime/<session_id>`. Пока marker существует,
`PreToolUse` хук `bypass-check.sh` возвращает harness'у
`permissionDecision: "allow"` для любого tool-вызова, и окна подтверждения
не появляются.

Продолжают работать **без отмены даже при активном bypass**:
- `permissions.deny` из `.claude/settings.json` (защита `.git/`, `.env`,
  форс-пушей, ребейзов и т.п.),
- хук `bash-no-var-paths.py` — блокирует составные bash-команды с
  shell-переменными в путях,
- встроенная защита harness на путь `.claude/` (нельзя обойти хуками).

**Обязанность модели:** когда пользователь пишет `да!` и bypass-режим
включается, в своём ответе ты ПЕРВОЙ СТРОКОЙ обязан крупно и жирно
уведомить об этом, чтобы пользователь сразу видел изменение режима.
Формат:

```
# 🚨 **BYPASS-РЕЖИМ ВКЛЮЧЁН** 🚨
```

или эквивалентный заголовок h1 + **жирным**. Далее — обычный ответ по сути
запроса. Уведомление показывается **только в том ответе**, где произошла
активация (т.е. когда пришёл system-reminder от `UserPromptSubmit` хука
с текстом «BYPASS-РЕЖИМ ВКЛЮЧЁН»). В последующих ответах этой же сессии
заголовок не повторять — bypass уже активен, второе напоминание избыточно.

Отключение происходит автоматически при закрытии сессии
(`SessionEnd` хук `bypass-cleanup.py` удаляет marker-файл).
Ручного слова для отключения нет.

## Отображение времени сообщений пользователя

`UserPromptSubmit` хук `.claude/hooks/inject-timestamp.py` добавляет в
`additionalContext` строку формата `[user message sent at YYYY-MM-DD HH:MM:SS]`.

**Обязанность модели:** когда такая строка пришла в контексте сообщения
пользователя, **ПЕРВЫМ БЛОКОМ ответа** (до любого другого текста)
показывать её в формате:

```
📬 *сообщение получено: YYYY-MM-DD HH:MM:SS*
```

(значок 📬 + курсив `*…*`). Цвет даёт инфраструктура из директории
`.claude/patches/`:

- **`claude-custom.css`** — каноничные стили (правило для класса
  `.claude-ts-line`).
- **`claude-custom.js`** — JS-наблюдатель, навешивает `.claude-ts-line`
  на абзацы, начинающиеся с 📬.
- **`claude-custom-config.toml`** — настройки (`logs`, `pollIntervalMs`,
  `throttleMs`, `visibilityRefreshDelayMs`, `debugOverlay`); читается
  хуком через `tomllib` (stdlib Python 3.11+),
  TOML нативно поддерживает `#`-комментарии. Хук валидирует наличие
  и тип каждого ожидаемого параметра; при отсутствии или некорректном
  значении эмитит в `additionalContext` строку с маркером
  `[claude-custom-config WARNING]` — модель **обязана** сообщить
  пользователю о проблеме в своём ответе (см. правило ниже).

Хук `.claude/hooks/patch-claude-webview.py` вызывается на `SessionStart`
и `UserPromptSubmit` (см. `.claude/settings.json`). Он:
1. Копирует `claude-custom.css` в `webview/claude-custom.css` каждой
   установленной версии расширения Claude Code.
2. Инлайнит `claude-custom.js` + JSON-конфиг внутрь bootstrap-блока
   в `webview/index.js` (CSP блокирует `<script src>` к webview-ресурсам,
   поэтому не отдельный файл, а инлайн в уже доверенный index.js).
3. Чистит устаревшие блоки/файлы от прошлых версий схемы.

В рантайме инлайн-JS:
- Подгружает `claude-custom.css` через `<link rel="stylesheet">` (CSS
  CSP пропускает).
- Каждые `pollIntervalMs` мс пересоздаёт `<link>` с `?t=<timestamp>` —
  cache-bust, благодаря чему изменения CSS-файла подхватываются
  во ВСЕХ открытых вкладках без `Reload Window`.
- `MutationObserver` дополнительно вызывает refresh на DOM-мутациях
  (с throttle `throttleMs`).

**Из этого формат строгий**: строка с 📬 и курсивом должна быть
**именно первым параграфом ответа** ассистента, без других элементов
перед ней. JS ищет `[data-testid="assistant-message"] p`, у которого
text-content начинается с `📬 ` — и только им вешает класс.

Прошлые попытки выделить цвет средствами самого markdown не сработали:
inline HTML `<span style="color">` / `<font color>` выводятся как
текст; ```diff``` code-block — подсветка не применяется в чат-панели;
GitHub-alert `[!TIP]` тоже не рендерится; CSS-селектор `:has()` тоже
не отрабатывает в Electron этого webview; `fetch` к vscode-resource
блокируется CSP `connect-src` — поэтому горячая перезагрузка
сделана через `<link>` с cache-bust query.

Workflow редактирования стилей:
- **Менять только CSS** (`claude-custom.css`) — изменения применяются
  «горячо», максимум через `pollIntervalMs`. Новый `Reload Window`
  не нужен.
- **Менять JS или конфиг** (`claude-custom.js`,
  `claude-custom-config.toml`) — bootstrap пересобирается при следующем
  `UserPromptSubmit`/`SessionStart` хуке, но в уже открытых webview
  применится только после `Developer: Reload Window` или закрытия-
  открытия панели Claude Code.

**Обязанность модели — реагировать на ошибки конфига.** Если в контексте
сообщения пользователя пришла строка с маркером
`[claude-custom-config WARNING]`, модель **обязана** в ответе показать
пользователю содержимое этого предупреждения в видимом блоке (например,
в шапке ответа после строки 📬, перед основным ответом). Список
проблем — это построчное перечисление параметров TOML-конфига, которых
не хватает или которые имеют неверный тип/значение. Игнорировать
предупреждение нельзя — если хук его эмитит, для пользователя это
важно: иначе webview-патч работает на встроенных JS-fallback'ах вместо
явных значений.

**То же самое для маркера `[csp-patch WARNING]`.** Его эмитит
`.claude/hooks/patch-extension-csp.py` на `SessionStart`, когда
CSP-meta тег в `extension.js` не распознан либо `connect-src` был
только что дописан. Модель **обязана** показать текст пользователю:
без `connect-src` webview теряет весь `fetch` — пинг 📡 показывает
`csp_blocked`, а locale-drift и models-list не доходят до
`http-server.py`. После свежего патча нужен `Developer: Reload Window`:
Extension Host читает `extension.js` только при загрузке.

**И для маркера `[exthost-restart WARNING]`.** Его эмитит тот же
`patch-extension-csp.py` — он владеет **обоими** патчами `extension.js`
(второй патч дописывает в конец файла блок перезапуска extension host,
см. раздел «Кнопка Accs»). Маркер приходит, когда блок только что
вставлен или обновлён, либо когда файл не удалось прочитать/записать.
В первом случае нужен `Developer: Reload Window`, во втором смена
аккаунта останется без автоматического применения.

Держать оба патча в одном хуке обязательно: хуки одного события
выполняются параллельно, и два процесса, переписывающих один и тот же
мегабайтный бандл, затрут правки друг друга — ровно как `localize.py`
затирал `patch-extension-settings.py` (прецедент выше). Новый патч
`extension.js` добавлять **в этот же файл**, а не отдельным хуком.

**И для маркера `[http-server WARNING]`.** Его эмитит
`patch-claude-webview.py`, когда не смог поднять `http-server.py` на
порту 18923 — обычно потому, что порт занят посторонним процессом.
Пока это так, webview остаётся без кнопок Cache и ByPass, пинга 📡
и детектора locale-drift: все они ходят в этот сервер.

Живость сервера определяется **ответом на `GET /ping`**, а не
PID-файлом. Прецедент (2026-08-17): файл пропал при живом процессе,
`_is_http_server_running()` вернул False, хук поднял второй инстанс,
тот не смог занять порт и молча умер — правки в `http-server.py`
перестали подхватываться, и это выяснилось только вручную. Обратный
случай не лучше: после SIGKILL файл остаётся, а `os.kill(pid, 0)`
может попасть в чужой процесс с переиспользованным pid.

**Сервер — синглтон на проект и общий для всех окон**, поэтому на
`SessionEnd` он НЕ гасится. Прецедент (2026-08-18): остановка висела на
`SessionEnd`, а он прилетает и от закрытия окна, и от каждого
`Reload Window` — сервер падал у всех остальных окон, и до ближайшего
сообщения webview получал «недоступен». От дубликатов защищают три
слоя: проверка `/ping` перед запуском, межпроцессный `flock` на
`hooks-runtime/http-server.lock` (хуки разных окон срабатывают
одновременно), и отказ `bind` в самом сервере — проигравший гонку
инстанс пишет строку в журнал и выходит с кодом 0, не трогая pid-файл
(pid пишется только после успешного `bind`).

**Журнал сервера** — `.claude/hooks-runtime/http-server.log`, включается
параметром `serverLog` в `claude-custom-config.toml`. Пишут обе стороны:
сервер (старт, полученные сигналы, ошибки запросов, завершение) и
`patch-claude-webview.py` (почему решил перезапустить или погасить).
Без второй половины причину остановки не определить — в журнале был бы
просто обрыв записей. Быстрый просмотр: `python3 .claude/hooks/hook_log.py 40`.

Прецедент (2026-08-18): обработчик SIGTERM звал `server.shutdown()`
напрямую. Он блокируется до выхода `serve_forever()`, а выполняется
внутри него в главном потоке — дедлок, порт остаётся занятым, сервер
перестаёт принимать соединения. В журнале это выглядит как строка
«получен сигнал 15» без следующей за ней «завершение». Звать
`shutdown()` только из отдельного потока.

`/ping` отдаёт ещё и `script_mtime` — время правки исходников сервера
на момент его старта. Хук сравнивает его с текущим и перезапускает
сервер, если тот работает со старым кодом: «жив» не значит «актуален».
Набор отслеживаемых файлов задан в `_sources_mtime()` внутри
`http-server.py` — добавил серверу новый локальный импорт, впиши его
туда, иначе изменения в нём не будут поводом для перезапуска.

**И для маркера `[ext-settings WARNING]`.** Его эмитит
`.claude/hooks/patch-extension-settings.py`, когда вписал в манифест
расширения новый пункт настроек (нужен `Developer: Reload Window`,
иначе пункта не будет в Settings UI) либо не смог этого сделать.
Повторные сообщения гасятся маркер-файлом
`hooks-runtime/ext-settings-applied.json`, поэтому если предупреждение
пришло — оно означает реальное изменение, а не рутину.

**Файлы расширения правятся только атомарно и под локом.** Это не
стилистика, а следствие поломки 2026-08-31, стоившей вечера работы.

`webview/index.js` (5 МБ), `extension.js` и `package.json` переписывают
сразу несколько наших процессов: `patch-claude-webview.py`,
`localize.py`, `patch-extension-csp.py` и `patch-extension-settings.py`
стартуют на SessionStart одновременно, в каждом открытом окне свой
комплект, а `http-server.py` дёргает патчер ещё и на каждую смену
TOML-конфига. В журнале за один рабочий день 91 случай, когда два и
более патчера стартовали в пределах 0.3 с; рекорд — восемь.

Прямой `open(path, "w")` усекает файл и наполняет его несколькими
системными вызовами, поэтому два писателя оставляют на диске смесь
двух версий. Для `index.js` смесь особенно коварна: у всех писателей
совпадает четырёхмегабайтный префикс с кодом приложения, а расходятся
только хвосты с блоками-маркерами. Размер выглядит правдоподобно, код
приложения цел, но маркеры разъезжаются (наблюдали «один BEGIN, два
END»). Синтаксическая ошибка в любом месте убивает бандл целиком —
и ВСЕ webview расширения (центральные вкладки, правая панель, список
сессий) открываются пустыми, хотя extension host жив и по кругу
отвечает `Getting authentication status`.

Хуже всего, что само это не лечится: `_upsert_marker_block`
переписывает только участок между первым BEGIN и первым END, а мусор
за его пределами переживает любой следующий запуск. Ни откат
репозитория, ни переименование `.claude` не помогают — порча живёт в
файле расширения, а не у нас. Тогда помогла только полная перезапись
`index.js` хуками другого проекта.

Отсюда три обязательных слоя, все в `.claude/hooks/ext_patch.py`:

- **`atomic_write`** — запись через временный файл рядом + `os.replace`.
  Читатель видит либо старое содержимое целиком, либо новое.
  Воспроизведение гонки: было 24 порчи из 30 прогонов, стало 0.
- **`patch_lock`** — межпроцессный `flock` вокруг всего цикла
  «прочитал → изменил → записал». Атомарность не спасает от потери
  правки: два процесса читают файл до чужой записи, и второй затирает
  первого устаревшим снимком. Проверка: без лока блок терялся в 15
  прогонах из 15, с локом — 0 из 15. Лок машинный
  (`~/.cache/claude-code-ext-patch.lock`), а не проектный: файлы
  расширения одни на все окна и проекты, и вчера их переписали хуки
  соседнего проекта — проектный лок такого писателя не остановил бы.
- **эталон `index.js.original`** рядом с бандлом, внутри папки версии
  расширения (обновление расширения заводит его заново). Патчер
  проверяет маркеры ДО правки и разбор бандла ПОСЛЕ реальной записи,
  восстанавливая файл из эталона. Раньше эталон был только у
  `package.json`, и `index.js` чинить было нечем.

Новый блок в файле расширения обязан быть вписан в таблицу
`ext_patch.BLOCK_MARKERS`, иначе он попадёт в эталон и после каждого
восстановления будет накладываться сам поверх себя.

**И для маркера `[webview-repair WARNING]`.** Его эмитит
`patch-claude-webview.py`, когда бандл оказался повреждён и был
восстановлен из эталона, либо когда после наложения нашего блока он
перестал разбираться (то есть в `claude-custom.js` синтаксическая
ошибка) и блок пришлось откатить. Модель **обязана** показать текст
пользователю: в первом случае нужен `Developer: Reload Window`, во
втором — расширение работает, но наш JS отключён до починки скрипта.
Отдельный случай — «эталона рядом нет»: тогда бандл не спасти изнутри,
нужна переустановка расширения.

**Диагностика webview (этап 56).** Родилось из отказа 2026-09-01:
вкладки пусты, при этом бандл цел (код приложения байт в байт равен
эталону), наш JS исполняется, протокол webview работает, исключений
нет — и назвать виновника было нечем. Теперь в bootstrap стоят:

- **Сборщик ошибок**: `window.onerror`, `unhandledrejection` и
  try/catch вокруг всего инлайн-JS (без обёртки падение одного модуля

**Воркеры Monaco в поставке расширения отсутствуют** — ни каталога
`vs/`, ни одного файла воркера. `import('…/vs/language/css/cssWorker.js')`

Это компенсирует отсутствие меток времени в UI VSCode-расширения —
пользователь хоть где-то видит, когда его сообщение дошло до модели,
а цвет визуально отделяет служебную метку от тела ответа.

Если в контексте нет строки `[user message sent at ...]` — ничего не показывать
(значит хук не сработал или это системное сообщение).

Правило работает независимо от bypass-режима и не конфликтует с
уведомлением `# 🚨 BYPASS-РЕЖИМ ВКЛЮЧЁН 🚨` — если оба события случились
одновременно (bypass включился этим же сообщением), порядок:
1. строка времени 📬
2. заголовок BYPASS (если применимо)
3. обычный ответ по сути запроса.

Разграничение со словом `да` из секции «Контрольные точки»:
- `да` / `ок` / `продолжай` (без `!`) → переход к следующей фазе, обычный
  режим подтверждений сохраняется,
- `даа` (две «а», без `!`) → идти до конца плана без вопросов «Продолжать?»
  (правило модели, harness-промпты остаются),
- `да!` (с `!`) → bypass tool-промптов harness до конца сессии.
  Ортогонально правилам фаз: между фазами всё равно коммит, если нет
  одновременно `даа`/`да!` комбинации.

## Смайлики в поле ввода чата

В `claude-custom.js` три IIFE-модуля, отвечающих за эмодзи. Каждый
защищён своим флагом `window.__claude*Installed` и включается
параметром из `claude-custom-config.toml`:

- **EMOJI CATALOG** — данные (символ, shortcode, ключевые слова
  на русском и латинице) и поиск. Регистрируется в
  `window.__claudeEmojiCatalog` всегда, флага не имеет: это общая
  зависимость двух модулей ниже.
- **EMOJI PICKER** (`emojiPicker`, `emojiRecentLimit`) — кнопка 😀
  слева от микрофона в правом верхнем углу поля ввода
  (`.micButtonWrapper_*`), панель с поиском, табами категорий
  и блоком «Недавние» (localStorage, ключ `claudeCustomEmojiRecent`).
  Микрофон рендерится только при `speechToTextEnabled`, поэтому есть
  запасное место — футер `.inputFooter_*` рядом с меню `/`.
  Расположение выбирается **не в TOML**, а в VSCode Settings UI —
  пункт `claudeCode.emojiButtonPlacement` (mic | footer). Цепочка:
  `patch-extension-settings.py` вписывает пункт и в `package.json`
  расширения, и в бэкап `package.json.original` (иначе `localize.py`,
  восстанавливая манифест из бэкапа, стирает его),
  `patch-claude-webview.py` читает значение из
  settings.json VSCode в конфиг bootstrap, а `claude-custom.js`
  опрашивает `http-server.py` (`/vscode-settings`) раз в 5 секунд —
  поэтому смена настройки применяется без `Reload Window`.
  Все наши пункты помечены тегом `claude-custom-patch` (фильтр
  `@tag:claude-custom-patch` в Settings UI) и маркером 🧩 в
  `markdownDescription` — покрасить строку нельзя, Settings UI живёт
  в оболочке VSCode, куда наш инжектор не достаёт.
- **EMOJI AUTOREPLACE** (`emojiAutoReplace`) — автозамена при наборе:
  `:)` → 🙂, `<3` → ❤️, `:rocket:` → 🚀.

Что важно помнить при правках этих модулей:

1. Composer — это `div[contenteditable="plaintext-only"]`, а не
   textarea, и он React-controlled. Прямая запись в `textContent`
   теряется при следующем ре-рендере; вставлять только через
   `document.execCommand('insertText')` (тот же приём, что в
   `triggerSlashCommandViaInput`).
2. Кликам по панели и по кнопке 😀 нужен `preventDefault` на
   `mousedown` — иначе фокус уходит из composer'а и вставка
   промахивается мимо каретки.
3. React перерисовывает поле ввода, поэтому кнопка переустанавливается
   MutationObserver'ом плюс таймером; проверка «уже вставлена» идёт
   по наличию `.claude-emoji-btn` внутри `.inputContainer_*`, а не по
   флагу-атрибуту. Контейнер микрофона переводится в flex классом
   `claude-emoji-mic-host` (иначе 😀 встаёт над микрофоном), а полю
   ввода добавляется правый отступ через `claude-emoji-inline` —
   штатные 36px рассчитаны на одну иконку. Оба класса вешает JS:
   `:has()` в этом webview не работает.
4. **Поле ввода рендерит текст прозрачным** (`color:#0000`), видна
   только каретка; сам текст рисует зеркальный `.mentionMirror_*`
   поверх него (`position:absolute; inset:0`). Любое изменение
   геометрии — padding, ширина, шрифт — обязано применяться к **обоим**
   элементам. Прецедент (2026-08-18): правый отступ под кнопку 😀
   поставили только настоящему полю, и невидимый текст стал
   переноситься раньше видимого. Каретка следует за невидимой
   раскладкой, буквы — за зеркалом; на каждой новой строке расхождение
   росло, курсор уезжал вперёд на всё большее число символов. На одной
   строке не заметно, поэтому проявилось только с третьей.
5. В автозамене паттерны разделены на мгновенные и отложенные.
   Отложенные (`:D`, `:o`, `:3`, `xD`) ждут пробела — иначе `:o`
   схлопнется в 😮 посреди набора `:ok_hand:`. Слева от паттерна
   требуется пробел или начало строки, иначе `http://` и `C:/Users`
   превращаются в мусор. Новые паттерны добавлять в ту таблицу,
   которая соответствует этому правилу, и прогонять кейсы
   `http:/`, `10:00`, `|---:|`, `xDoc`, `пункт 8)`.

## Пункт меню «Общие настройки…»

Модуль **SETTINGS MENU FIX** в `claude-custom.js` (параметр
`fixSettingsMenuItem`) чинит баг расширения 2.1.220: пункт меню `/`
«Настройки → Общие настройки…» вместо настроек расширения отправлял
в чат слэш-команду `/config`.

Причина — коллизия id внутри расширения. Пункт регистрируется с
`id: k6.config`, где `k6.config === "slash-command-config"`, а
слэш-команды CLI регистрируются как `` `slash-command-${invocation}` ``
— для новой команды `/config` получается тот же самый id. Регистрация
команды перекрывает обработчик пункта. Внешний признак: оба пункта
подсвечиваются в меню одновременно.

Патч перехватывает click в capture-фазе, опознаёт пункт по лейблу
(RU/EN, оба варианта многоточия) и вызывает `openConfig()` — метод
контекста приложения, который достаётся через React-fiber: сначала
подъёмом по `.return` от кликнутого элемента, при неудаче — обходом
дерева от `#root`. Если контекст не найден, событие НЕ блокируется:
пусть отработает штатное (неверное) поведение, это лучше мёртвой
кнопки. Признак контекста — наличие методов `openConfig` и `openHelp`.

Если Anthropic починит коллизию у себя — поставить
`fixSettingsMenuItem = false`.

## Кнопка Accs — смена провайдера и перезапуск расширения

Кнопка `Accs` в футере переключает аккаунты провайдеров: каждый
`~/.claude/settings*.json` — отдельный аккаунт, выбор пункта подменяет
им активный `settings.json`. Файловая часть — `account_switcher.py`,
транспорт — `GET/POST localhost:18923/accounts`, UI — модуль
`ACCOUNT SWITCHER BUTTON` в `claude-custom.js`. Включается параметром
`accountsButton`.

**Почему одной подмены файла мало.** `env` из `settings.json` применяет
к себе процесс `claude`, и делает он это при своём старте. А стартует
он **один раз на активацию extension host**, не на каждый диалог: в
логе расширения (`~/.config/Code/logs/*/window*/exthost/Anthropic.claude-code/`)
строк `Spawn-env probe captured` ровно столько, сколько было активаций.
Поэтому применить смену можно только новым процессом CLI.

**Что для этого делается.** Минимально достаточное действие —
`workbench.action.restartExtensionHost`, а не `Reload Window`: окно,
редакторы, вкладки и терминалы остаются на месте. Но рестарт хоста
обновляет только tree view (сессии слева, агенты справа): контент
webview-вкладок — диалоги посередине — это iframe в окне VSCode, он
переживает смерть extension host и остаётся со старым JS. Поэтому блок
зовёт ещё `workbench.action.webview.reloadWebviewAction` (то же, что
«Developer: Reload Webviews»). Webview команды VSCode не исполняет,
поэтому цепочка такая:

1. Модалка после переключения (`accountsRestartPrompt`) шлёт
   `POST /restart-exthost` со своим `sessionId`.
2. `http-server.py` кладёт заявку с токеном и `sessionId` в
   `.claude/hooks-runtime/restart-exthost-request.json`.
3. Блок `[claude-exthost-restart]`, дописанный в `extension.js`
   хуком `patch-extension-csp.py`, читает заявку раз в секунду, пишет
   подтверждение в `restart-exthost-ack.json`, спустя ~1.6 с оставляет
   себе заявку `restart-exthost-reload.json` и вызывает команду рестарта
   хоста. Пауза — чтобы модалка успела получить ack и отрисовать статус
   (она опрашивает ack каждые 400 мс).
4. Новая жизнь хоста читает эту заявку при старте и через ~1.5 с
   переоткрывает вкладку (см. ниже). Остальные оживают сами, когда
   пользователь на них переключится. Весь путь от нажатия до готовой
   панели — около 3 секунд.
5. Модалка следит за подтверждением через `GET /restart-exthost`;
   молчание за 4 секунды означает, что блок не активен, и она честно
   говорит про ручной `Developer: Reload Window`. После ack она
   закрывается сама через 20 с — на случай, если переоткрытия не
   случилось: висеть поверх окна, перекрывая ввод, она не должна.

Ход цепочки виден в `hooks-runtime/exthost-restart.log` — его пишет сам
блок. Он же логирует `createWebviewPanel` и `deserializeWebviewPanel`,
подменяя эти методы `vscode.window` при загрузке модуля (то есть до
`activate()`). Без такого журнала разбирать поведение webview после
рестарта нечем: со стороны видно только «вкладка пустая».

**Активную вкладку закрывают и открывают заново по `sessionId`.**
Панель, созданную умершим хостом, VSCode оживляет (просит у расширения
`deserializeWebviewPanel`) в момент, когда она СТАНОВИТСЯ видимой, —
скрытые вкладки поэтому оживают сами при первом показе. Активную он не
трогает: она видима, содержимое цело, повода вмешиваться нет. Поэтому
блок закрывает её (`tabGroups.close`) и зовёт
`claude-vscode.editor.open(sessionId, undefined, ViewColumn.Active)` —
команда расширения, которая создаёт панель заново той же переписке в
той же группе (`createPanel(sessionId, …)`). Колонку передаём именно
`Active`: конкретный номер расширение трактует иначе и заодно
переставляет себе предпочитаемое место.

**Имя сессии знает только сам webview.** Поэтому `sessionId`
(`window.__claudeSessionId`) идёт в теле `POST /restart-exthost`,
оттуда в файл заявки, оттуда — в поручение преемнику. Без него блок
вкладку не трогает вовсе: закрыть, не умея открыть ту же переписку,
хуже, чем оставить мёртвую панель — её хотя бы видно в списке. По той
же причине сверяется заголовок вкладки: если за время рестарта
переключились на другую, она живая и трогать её нельзя.

`claude-vscode.reopenClosedSession` для этого НЕ годится, хотя название
обещает ровно то, что нужно: он берёт сессию из списка недавно
закрытых, а список живёт в памяти хоста. Новый хост про закрытую нами
панель ничего не знает, список пуст — команда молча уходит в свой
fallback, и вместо переписки открывается пустой диалог.

Два более мягких способа проверены и не работают — не возвращать их:

- **`workbench.action.webview.reloadWebviewAction`** («Developer: Reload
  Webviews») обнуляет содержимое панели, а отвечать на запрос контента
  после смерти владельца некому: вкладка становится пустой при живом
  заголовке. По журналу `hooks-runtime/exthost-restart.log` видно, что
  после штатного `Reload Window` строка `deserializeWebviewPanel` для
  активной вкладки приходит через ~50 мс, а после рестарта хоста не
  приходит вовсе.
- **Показ заново** (уйти на соседнюю вкладку и вернуться) VSCode поводом
  для восстановления не считает: DOM остаётся прежним со всем, что на
  нём было, — модалка Accs так и висела поверх пустой вкладки.

Само поручение оставляется на диске (`restart-exthost-reload.json`),
потому что код блока живёт в умирающем процессе и «после рестарта»
исполнить ничего не может — оживление выполняет уже его преемник.

Файл заявки намеренно **не удаляется** после исполнения: окна с тем же
воркспейсом перезапускают хост каждое по-своему, и первое же удаление
лишило бы остальные перезагрузки вкладок. От вечного действия защищает
TTL в 60 секунд, от повторов внутри процесса — то, что заявка читается
один раз при старте, а не в опросе.

**Отказ откатывает подмену.** «Позже», Escape и клик мимо окна не просто
закрывают модалку — они возвращают `settings.json` прежнему аккаунту
(тому, на котором реально работает текущий процесс). Иначе на диске
остался бы один провайдер, а в работающей сессии — другой, и ближайшая
посторонняя перезагрузка окна молча сменила бы модель. Прежний аккаунт
запоминается ДО запроса на подмену: после неё сервер возвращает уже
новый список, и узнать, откуда ушли, будет не по чему. Если откат не
удался, окно остаётся открытым с ошибкой — молча закрыться нельзя,
на диске в этот момент чужой аккаунт. После нажатия «Перезапустить»
откат запрещён: хост вот-вот прочитает новый файл.

**Полоски лимитов в строке.** Строка аккаунта claude.ai — в два ряда:
первый «Anthropic Pro (почта)» (тариф и почту отдаёт
`anthropic_identity()`, endpoint у OAuth-аккаунта всегда одинаковый и
ничего не сообщает), второй — шкалы по окнам лимитов: «5 ч» (сессия)
и «7 дн» (неделя), у Max к ним добавляются окна по моделям. В подсказке
— процент, время до сброса и возраст данных; время до сброса продубли
ровано текстом внутри самой шкалы. Включается параметром
`accountsUsageBars`; серверная часть — `anthropic_usage()`
в `account_switcher.py`, поле `usage` приходит внутри самого аккаунта
в ответе `/accounts` (а не отдельным endpoint'ом — тогда его пришлось
бы запрашивать и после переключения, и после сохранения настроек:
список перерисовывается по ответам обоих).

- **Числа читаются из кэша Claude Code, а не запрашиваются нами.**
  CLI сам ходит в `api.anthropic.com/api/oauth/usage` и кладёт ответ
  в `~/.claude.json` (`cachedUsageUtilization`). Свой запрос требовал
  бы OAuth-токен из `~/.claude/.credentials.json`, а он живёт часами
  и требует обновления — соперничать с CLI за этот файл ради чисел,
  которые он и так сохранил, незачем.
- **Отсюда следует, что свежесть не наша.** Кэш обновляет CLI, пока
  работает на OAuth-логине; сессия через стороннего провайдера его не
  трогает. Поэтому наружу уходит `ageSec`, подсказка называет возраст,
  а после получаса полоски приглушаются. Молча показать вчерашние
  проценты как сегодняшние — единственный по-настоящему плохой
  вариант: именно ради них панель и открывают.
- **Кому полоски, решает тип логина, а не имя файла.** Их получает
  аккаунт, у которого в `env` нет ни `ANTHROPIC_BASE_URL`, ни
  `ANTHROPIC_API_KEY`, ни `ANTHROPIC_AUTH_TOKEN`. Правило то же, что
  у списка аккаунтов (маска вместо перечня): `settings_mac.json` по
  имени выглядит «своим», но смотрит на east-api — полосок там быть
  не должно. И наоборот: два файла на одном OAuth-логине покажут
  одинаковые числа, потому что лимит один на логин, а не на файл.
- **Кэш сверяется с `oauthAccount.accountUuid`.** После смены логина
  в нём какое-то время лежат проценты прежнего аккаунта; при
  расхождении не показываем ничего.
- **Список окон явный.** Рядом с `five_hour` в том же объекте лежат
  окна под кодовыми именами (`nimbus_quill`, `cinder_cove`, …).
  Что они означают, неизвестно, поэтому рисуем только знакомые —
  «все непустые» превратило бы догадку в интерфейс.
- **Полоски не перехватывают клик.** Они внутри строки-кнопки, а
  строка целиком означает «переключиться на этот аккаунт»: мёртвая
  зона в её правой половине была бы неожиданностью.

**Обновление полосок (этапы 54–55), включая прецеденты.**

- **Числа приходят двумя путями.** Мгновенно — из кэша (выше), но он
  стареет, пока никто не спрашивает. Поэтому при открытии панели
  webview просит свежие числа у самого расширения тем же вызовом
  `session.getUsage()`, каким их берёт окно «Аккаунт и расход»;
  объект сессии достаётся из React-fiber по наличию метода
  `getUsage`. Побочный эффект тут главный: CLI при этом перезаписывает
  свой кэш, и свежие числа достаются серверу и Mood. Кэшированные
  значения показываются сразу и пульсируют, пока идёт запрос.
- **Таблица окон продублирована в JS и Python** (`USAGE_WINDOWS`
  в `account_switcher.py` и в модуле ACCOUNT SWITCHER BUTTON): числа
  приходят двумя путями — кэш через сервер и живой ответ расширения
  — и одно окно не должно называться в них по-разному. Правишь
  список — правь оба места.
- **Цвет шкалы говорит об уровне расхода, а не об окне:** до 25%
  зелёный, до 50% жёлтый, до 75% оранжевый, дальше красный. Оттенки
  взяты у секторов индикатора Mood (`.claude-mood-arc-*`). Границы
  четвертей считает JS и кладёт в `data-level` — порог живёт в одном
  месте. Процент красится цветом шкалы, подпись окна всегда белая:
  она называет окно, а не оценивает его.
- **Текст внутри шкалы — одним слоем и одной парой цветов.** Проблема:
  надпись лежит на пяти разных фонах, и ни один цвет текста не даёт
  порога WCAG на всех (тёмный проигрывает на подложке, белый — на
  заливках). Решение — подобранная на стенде пара: текст `#000dff`,
  подложка `#d5fff5` (7.8:1), поверх — гало `text-shadow: 0 0 2px
  #f6f5f4` ×4 для читаемости на заливках (у гало нет числа контраста,
  WCAG считает только сплошные пары).
- **Прецедент: менять цвет текста по границе заливки двумя слоями
  нельзя** (фаза 55.2). Обрезка верхнего слоя по ширине заливки даёт
  белую кайму на буквах: сглаживание глифов смешивается с нижним
  ТЕКСТОМ, а не с фоном. На 10px нечитаемо; вернули одним слоем.
- **Стенды в `tmp/`** — автономные HTML, в webview не
  участвуют: `usage-text-picker.html` (круговое колесо HSV, параметры
  текста, две цели — текст/подложка, живой расчёт контраста) и
  `usage-readability-variants.html` (шесть способов читаемости
  рядом). Подбор «на глаз» в живой панели — это пять Reload Window
  на вариант; стенд снимает проблему.

**Шестерёнка в строке — правка настроек аккаунта.** Открывает под
строкой форму из двух разделов: «настройки» (скалярные ключи верхнего
уровня — `model`, `language`, `effortLevel`, …) и «env · переменные
окружения». У каждой строки — поле значения, значок `?` с описанием
ключа и крестик удаления; внизу «+ настройка», «+ переменная» и
«Сохранить». Транспорт — `GET/POST localhost:18923/account-env`,
файловая часть — `read_account_config` / `write_account_config` в
`account_switcher.py`.

Раздел настроек появился потому, что у аккаунта Anthropic секции `env`
нет вовсе: форма для него открывалась пустой, хотя сам файл задаёт и
модель, и язык, и уровень усилий.

Что здесь важно и неочевидно:

- **Правится источник, а не активная копия.** У аккаунтов провайдеров
  это сам `settings_x.json`, а у базового — `settings.json.bak`, пока
  активен чужой аккаунт: в `settings.json` в этот момент лежит копия
  чужого файла. Отсюда же `source_path()` в `list_accounts()` — без неё
  строка «Anthropic» показывала бы чужой endpoint. Если правился
  активный аккаунт, рабочая копия `settings.json` обновляется следом:
  иначе правка не дожила бы до перезапуска, настройки читают именно
  из неё.
- **Что попадает в раздел настроек, решает тип, а не список.** Панель
  показывает скалярные ключи верхнего уровня; `permissions`, `hooks`,
  `mcpServers` и прочие структуры отсеиваются, потому что полем
  «ключ→значение» их не отредактировать, а сохранить как текст значило
  бы их испортить. Правило по типу выбрано намеренно: незнакомая
  настройка-скаляр должна появляться в панели сама — по той же причине,
  по какой список аккаунтов сканирует маску, а не жёсткий перечень.
  Явно скрыты только `env` (у него свой раздел) и `$schema` (ссылка для
  редакторов JSON, к поведению CLI отношения не имеющая).
- **Отсутствующий раздел в POST означает «не трогать».** Пустой объект
  сервер понял бы как «удалить всё», а webview, загруженный до этой
  правки, шлёт одно `env` — и стёр бы настройки верхнего уровня.
  Bootstrap перечитывается только при `Reload Window`, так что такие
  окна живут до ближайшей перезагрузки. По той же причине endpoint
  остался `/account-env`, хотя разделов теперь два: переименование
  оставило бы их с мёртвой шестерёнкой.
- **Тип значения сохраняется.** `switchModelsOnFlag` должен остаться
  булевым, а не строкой «true», иначе расширение молча его отбросит.
  Тип берётся из справочника, при незнакомом ключе — из прежнего
  значения в файле, и лишь потом угадывается по самой строке
  (`_coerce_setting`). Поэтому же bool и enum рисуются списком, а не
  текстовым полем: значение вне enum'а расширение игнорирует, и
  настройка выглядит заданной, не действуя (ровно это случилось с
  `effortLevel: "max"` в `settings_mac.json` — в схеме 2.1.220 такого
  уровня нет). Текущее значение всё равно попадает в список, даже
  когда его там нет: показать «max» как «low» значило бы соврать
  про файл.
- **Пустой `env` не сохраняется как `{}`, а удаляется**: у базового
  аккаунта секции нет вовсе, и пустой объект был бы отличием без
  разницы.
- **`max` и `ultracode` сохраняются по-разному — это не одно и то же.**
  `max` в ключе `effortLevel` НЕ действует: валидатор настроек
  принимает только low/medium/high/xhigh, постороннее значение
  молча отбрасывается (`.catch(void 0)`), а `/effort max` помечен
  как session-only и в файл не пишется вовсе. Единственный способ
  держать max постоянно — env-переменная `CLAUDE_CODE_EFFORT_LEVEL=max`
  (её парсер проверяет по полному списку low..max и принимает;
  `med`=medium, `unset`/`auto` снимают; она же перебивает всё
  на сессию). А вот `ultracode` — самостоятельный булев ключ
  настроек: `"ultracode": true` в файле действует (форсирует xhigh
  плюс постоянную оркестрацию workflow), интерактивный
  `/effort ultracode` не сохраняется никогда. Для него нужны
  включённые workflow и xhigh-способная модель; триггер по слову
  «ultracode» в промпте управляется отдельным ключом
  `workflowKeywordTriggerEnabled` (по умолчанию включён).
- **Подсказки живут на сервере** (`ENV_HINTS` и `SETTING_HINTS` в
  `account_switcher.py`, приходят полем `hints`), а не в JS: правка
  текста там применяется перезапуском сервера по mtime, а в
  `claude-custom.js` потребовала бы `Reload Window`. Значок `?`
  показывается только у знакомого ключа — у незнакомого он обещал бы
  объяснение, которого нет; место под него держится всегда, иначе
  крестики соседних строк встали бы в разные колонки.
- **Значения ходят как есть, включая токены** — сервер слушает
  localhost, webview живёт на той же машине. В журнал они не попадают:
  там только имена ключей. Маски у значений нет (была, вместе с кнопкой
  «глаз», — убрана по просьбе пользователя): скрытое значение всё равно
  нельзя было сверить, не открыв его.
- **Шестерёнка лежит рядом со строкой, а не внутри.** Строка аккаунта —
  это `<button>`; вложенная кнопка невалидна и ломает клики. Поэтому
  разметка строки — обёртка `.claude-accs-item` c `.claude-accs-line`
  внутри. Клик по шестерёнке останавливает всплытие: иначе он дошёл бы
  до строки и переключил аккаунт вместо открытия формы.
- **Escape при фокусе в форме закрывает форму, а не панель.** Набирая
  значение, промахнуться мимо клавиши легко, а закрытая панель унесла бы
  с собой всю несохранённую правку.

Два свойства схемы перезапуска держатся на деталях, которые легко
сломать правкой:

- **Область действия.** Путь заявки блок выводит из корней воркспейса
  своего окна, а не из глобального места. Иначе перезапустились бы все
  окна VSCode разом, оборвав работу в чужих проектах.
- **Отсутствие цикла.** Токен заявки запоминается как базовый при
  первом же взгляде на папку. Поэтому заявка, вызвавшая перезапуск,
  после реактивации новой не считается. Убрать базовый снимок — значит
  получить бесконечный перезапуск хоста.

Если в сборке VSCode команды не окажется, блок откатывается на
`workbench.action.reloadWindow` и снимает подтверждение — смена
всё равно применится, но дороже. **Наличие команды проверяется
списком** (`vscode.commands.getCommands(true)`), а не по тому,
отклонился ли её промис. Прецедент (2026-08-31): откат висел на
обработчике ошибки `executeCommand`, а при удачном рестарте хост
умирает и все pending-RPC отклоняются как «Canceled» — обработчик
успевал стереть заявку на перезагрузку вкладок перед самой смертью
процесса. Со стороны это выглядело как «рестарт прошёл, вкладки не
обновились»: новый хост просто не находил поручения. Отличить
«Canceled» от настоящего «команды нет» по промису нельзя, поэтому
реагировать на его отклонение запрещено.

## Индикатор Mood — спидометр в футере

Слева от кнопки `Accs` стоит индикатор `Mood`: полукруглая шкала из
четырёх равных секторов (красный, оранжевый, жёлтый, зелёный) и
стрелка поверх неё. Модуль `MOOD GAUGE` в `claude-custom.js`,
стили — блок `MOOD GAUGE` в `claude-custom.css`, включается
параметром `moodGauge` в `claude-custom-config.toml`.

**Что измеряет: как часто теряется живой prompt-кэш.** Промах после
паузы длиннее `cacheKeepaliveTtlMinutes` неизбежен — TTL кончился,
перезапись оплатили бы при любом раскладе. Промах при паузе короче
TTL — потеря на ровном месте: кэш был жив, но ход его не застал.
Стрелка показывает долю таких ходов: потерь нет — зелёная зона,
изредка — жёлтая, каждый третий-второй ход — оранжевая, кэш не
доживает почти никогда — красная. Шкала значений линейная (0 — левый
край красного, 100 — правый край зелёного, границы секторов на
25/50/75), сама метрика раскладывается по ней так:

- ноль потерь → 94, единственное значение в зелёном. Зелёный обязан
  что-то гарантировать, поэтому «почти ноль» в него не попадает;
- остальное → от 74 (потери единичны) до 2 (кэш не доживает ни разу),
  линейно по доле.

**Второй фактор: раскрывалось ли контекстное окно.** Сессия, где
контекст хотя бы раз поднимался выше `moodContextGoal` (250k по
умолчанию), получает прибавку к оценке, не дотянувшая — вычет.
Сравнивается пик за сессию (`context_peak`), а не текущий контекст:
компактификация обнуляет окно, и по последнему ходу уже не понять,
докуда оно доросло. Поправка фиксированная (`CONTEXT_SHIFT`, ~половина
сектора) и главным фактором не становится — потери живого кэша важнее
размера окна. Пока ходов меньше `MIN_CHANCES`, поправка не
применяется ни в какую сторону: окно свежей сессии просто не успело
вырасти, и вычет за это говорил бы о темпе работы, а не о кэше.

Из-за поправки зелёная зона больше не означает строго «потерь нет»:
единичные потери при раскрывшемся окне тоже попадают в неё. Обратное
верно: ноль потерь при так и не выросшем окне остаётся зелёным, но
ближе к жёлтому.

Данные — `GET /cache-usage`, поля `early_misses`, `early_chances`
и `context_peak`.
**Разметка промахов живёт на сервере** (`explain_turns` в
`cache_usage.py`) и делается при выдаче, а не при разборе: в состоянии
лежит сырьё по каждому ходу (промах, пауза, контекст, модель), а
сравнение с TTL и поиск причины — уже на выходе. Поэтому и правка
`cacheKeepaliveTtlMinutes`, и новая запись в журнале аккаунтов
пересчитывают уже накопленную сессию, а не только будущие ходы.
Считают по одному ряду ходов и стрелка, и кривая истории: раньше
`collect()` брал ранние из `miss_gaps` (500 записей), а история — из
`turns` (3000), и в длинной сессии они разошлись бы.

Две детали, которые легко счесть лишними и убрать:

- **Знаменатель не меньше `MIN_CHANCES` (10).** Иначе первая же потеря
  на первом ходу даёт «1 из 1» — сто процентов и красную зону, хотя
  одна точка ещё ничего не значит. С ростом сессии ограничение
  перестаёт действовать само.
- **Запасной расчёт по `miss_log`**, если сервер не прислал
  `early_misses`. Нужен, пока в окне работает webview, загруженный до
  обновления сервера: доля выйдет заниженной, но это лучше серой шкалы.
  По той же причине отсутствие `context_peak` отключает поправку за
  контекст, а не трактуется как «окно не выросло».

## Промахи после переключений и раздел «История» (этап 61)

**Промах бывает трёх сортов, и путать их нельзя.**

- **Неизбежный по времени** — пауза длиннее TTL: кэш истёк бы сам.
- **Объяснённый** — между ходами сменилась модель или аккаунт. Другая
  модель это другой префикс, другой аккаунт — вообще другой провайдер;
  кэш в этот момент холодный по определению.
- **Ранний** — всё остальное. Только это и есть потеря на ровном месте,
  и только это считает индикатор Mood.

До этапа 61 объяснённые считались ранними, то есть Mood штрафовал за
собственное решение пользователя переключиться. На проверочной сессии
из 487 ходов таких промахов было четыре (все — переходы Anthropic ↔
Z.AI), и **каждое переключение стоило промаха**: ранних 22 → 19,
знаменатель 486 → 482.

**Объяснённый ход выбывает и из знаменателя.** Шанса у него не было,
а оставить его там — занизить долю потерь ровно в тех сессиях, где
переключались чаще всего.

**Приоритет у аккаунта, а не у модели.** Смена аккаунта обычно тянет
за собой и смену модели, и назвать причиной модель значило бы указать
на следствие.

**Смена модели видна из транскрипта, смена аккаунта — нет.** Поэтому
`account_switcher.py` пишет состоявшиеся подмены в
`hooks-runtime/account-events.jsonl` (JSONL, 500 последних). Разбирать
ради этого человеческие строки `http-server.log` значило бы завязаться
на его формат, а он ещё и ротируется по размеру.

**Откат пишется, но помечается `revert: true` и в историю не идёт.**
Отказ от перезапуска возвращает прежний аккаунт тем же самым запросом
`POST /accounts`, и отличить его от обычного переключения сервер сам
не может — признак сообщает модалка. Без него каждый отказ выглядел бы
как два переключения подряд, то есть объяснял бы промахи тем, чего не
происходило. А не писать вовсе — потерять след ровно в том случае,
когда откат сорвался и на диске остался чужой аккаунт.

**`<synthetic>` за модель не считается** — это служебная отметка CLI на
сообщениях об ошибках API. Сегодня такие записи отсеиваются нулевой
`usage`, но принять их за смену модели значило бы получить пару ложных
переключений на каждую ошибку.

### Раздел «История» в панели Usage

Бывшие «последние промахи». Лента по времени: промахи вперемешку со
сменами модели и аккаунта — причина рядом со следствием. Готовит её
сервер (`build_history`), поле `history` в `/cache-usage`.

- **Цвета разведены по смыслу, а не по тяжести.** Красный — аномалия
  (пауза короче TTL, кэш обязан был выжить), жёлтый — вытеснение по
  времени, приглушённый — промах после переключения (объясняет, а не
  тревожит), синий — сами события: они вообще не из палитры потерь.
- **Событие, до которого ход ещё не дошёл, показывается с пунктиром.**
  Переключился, открыл панель — видно, что зафиксировано. Без пометки
  оно читалось бы как обошедшееся без промаха, хотя кэш просто ещё
  не проверялся.
- **Диапазон сессии соблюдается сам собой:** события берутся из
  размеченных ходов. Для свежих, ещё не привязанных, стоит явная
  отсечка по началу сессии — журнал общий на проект, и чужие
  переключения здесь были бы враньём.
- **`miss_log` остаётся в ответе сервера** ради webview, загруженных до
  этой правки: bootstrap перечитывается только при `Reload Window`, и
  такое окно живёт до ближайшей перезагрузки. UI берёт `history`, а при
  его отсутствии рисует прежний список без событий.

Пока сервер не ответил (или молчит три опроса подряд — `FAIL_TOLERANCE`),
шкала обесцвечивается классом `claude-mood-nodata`: цветная шкала с
зелёной стрелкой утверждала бы «всё хорошо», хотя ответа ещё не было.
Период опроса — `moodPollSec`.

Подсказка индикатора многострочная — по строке на фактор, чтобы было
видно, откуда взялось положение стрелки.

Значение можно поставить руками: `window.__claudeMood.set(0..100)`,
`.get()`, внеочередной опрос — `.refresh()`. Это отладочный вход,
ближайший опрос перебьёт ручное значение своим.

Что важно помнить при правках:

1. **Это кнопка — с этапа 58.** Класс штатной `footerButton_`
   заимствуется, как у `Accs` и `Usage`: клик открывает окно истории,
   поэтому подсветка при наведении и курсор-указатель честны. До
   этапа 58 действовало обратное правило (`cursor: default`, никаких
   обработчиков) — ровно потому, что действия не было, и обещать его
   видом было бы неправдой. Появилось действие — изменился и вид.
2. **Оформление живёт в CSS, а не в атрибутах SVG** — цвета секторов
   (`.claude-mood-arc-1..4`, значения из общих `--claude-mood-1..4`
   на `:root`), толщина дуги, размер. CSS
   перечитывается горячо (cache-bust `<link>` раз в
   `pollIntervalMs`), поэтому палитру можно подбирать без
   `Reload Window`; правка JS потребовала бы перезагрузки окна.
   Те же переменные раздаются зонам графика истории, полоскам
   лимитов в Accs и обводке поля ввода — правка палитры меняет их
   все разом (см. «Обводка поля ввода цветом Mood»).
3. **Стрелка поворачивается CSS-свойством `transform`**, а не
   одноимённым атрибутом SVG: только по нему работает `transition`.
   Отсюда же `transform-box: view-box` — без него `transform-origin`
   считался бы по bounding box самой стрелки, и она вращалась бы
   вокруг своей середины, а не вокруг центра шкалы.
4. **Значение одно на окно.** Экземпляров индикатора в DOM столько,
   сколько открытых полей ввода; обновляются все сразу. Показывать
   в них разное было бы враньём — метрика-то одна.
   Session id берётся из `window.__claudeSessionId` (резолвер
   регистрирует `CACHE USAGE BUTTON` до проверки своего флага) —
   без него сервер отдал бы статистику чужой вкладки.
5. Порядок в футере — `Mood · Accs · Usage · Cache · ByPass` — держит
   `ensureOrder`, как у соседей: вставка при монтировании его не
   гарантирует, React пересоздаёт футер и порядок инициализации
   модулей не фиксирован.

**История шкалы — окно по клику (этап 58).** График значения по ходам
сессии: фон из тех же четырёх зон, что у самой шкалы, белая линия
поверх (цвет уже занят зонами — вторая цветовая шкала спорила бы с
первой), под ним сводка. По оси X номер хода, а не время: паузы между
ходами бывают часами, и на временной оси вся работа сжалась бы в
несколько пятен.

- **История не копится, а восстанавливается.** Данные приходят из
  `GET /mood-history`: сервер строит их пересчётом уже разобранного
  транскрипта (`mood_series` в `cache_usage.py`), поэтому история полна
  с первого хода сессии, включая ходы до появления самого окна.
  Накопление в localStorage дало бы историю «с сегодняшнего дня» и
  обнулялось бы при смене сессии.
- **В состоянии разборщика лежит сырьё, а не значения.** Ряд `turns`
  хранит по ходу: был ли промах, какая пауза, какой контекст. Сравнение
  паузы с TTL делается при выдаче — поэтому правка
  `cacheKeepaliveTtlMinutes` пересчитывает всю накопленную историю
  так же, как текущее положение стрелки.
- **Формула одна на кривую и на стрелку.** Сервер значение шкалы не
  считает: точки истории прогоняются через тот же `valueFor`. Вторая
  копия формулы однажды разошлась бы с первой, и объяснить, почему
  график и стрелка говорят об одном ходе разное, было бы нечем.
- **Ряд отдаётся отдельным endpoint'ом**, а не полем `/cache-usage`:
  тот опрашивается индикатором каждые `moodPollSec` секунд, и сотни
  точек гонялись бы вхолостую. Сессию оба ищут общим
  `_resolve_transcript` — разъехавшись, окно показывало бы не ту
  переписку, что стрелка.

Разметка SVG строится через `createElementNS`, а не `innerHTML`:
SVG живёт в своём namespace, а `innerHTML` упирается в Trusted Types
(тот же приём, что в `accsIcon`).

## Обводка поля ввода цветом Mood (этап 65)

Рамка поля ввода при фокусе штатно окрашена по режиму разрешений:
оранжевый — обычный, синий — план, серо-белый — «Править
автоматически», красный — bypass/auto. Параметр `inputRingColor`
(модуль `INPUT RING` в `claude-custom.js`) позволяет отдать её другому
признаку — сектору, в который смотрит стрелка Mood.

Смысл замены: индикатор в футере занимает 27×16 точек, а рамка
обрамляет то самое место, куда смотришь при наборе. Цена — режим
разрешений перестаёт быть виден цветом; он остаётся словом в футере.
Оба сразу невозможны — рамка одна, — поэтому это настройка, а не
поведение по умолчанию.

- **Подменяется переменная, а не сама рамка.** Расширение держит цвет
  в `--focus-ring-color` и меняет её правилами по `data-permission-mode`;
  `border-color` и `box-shadow` выводятся из неё. Свои правила про
  рамку разошлись бы с оригиналом на первом же обновлении расширения.
- **Селектор дублирует класс** (`.claude-ring-mood.claude-ring-mood[…]`).
  У правил расширения специфичность (0,3,0) — дубль даёт (0,4,0) и
  выигрывает по весу, а не по порядку подключения файлов: наш `<link>`
  пересоздаётся cache-bust'ом и встаёт последним не при любом способе
  загрузки страницы.
- **JS ставит номер сектора, цвет живёт в CSS.** Палитра вынесена в
  переменные `--claude-mood-1..4` на `:root` и раздаётся секторам
  шкалы, зонам графика истории, полоскам лимитов в Accs и этой рамке.
  Четыре копии одних значений разошлись бы, и «одна и та же тревога»
  стала бы выглядеть в разных местах по-разному.
- **Красить надо внутренний контейнер** — тот, которому расширение
  ставит `data-permission-mode`. У внешнего рамки нет вовсе, а
  унаследованную от него переменную внутренний перебил бы своим
  правилом при фокусе.
- **Значение приходит подпиской** (`window.__claudeMood.onChange`), а
  уровень отдаёт `level()` — 0..3 либо `null`. Свой таймер почти
  всегда заставал бы значение прежним: оно меняется раз в `moodPollSec`.
- **«Данных ещё нет» — штатная рамка, а не зелёная.** Шкала в этот
  момент обесцвечивается ровно потому, что утверждать «всё хорошо»
  рано. Так же и при выключенном `moodGauge`: красить нечем.
- **В DOM пишем только при смене значения.** Присваивание мутирует
  дерево независимо от того, изменилось ли оно, а каждая мутация будит
  общий наблюдатель — тот же капкан, в который однажды попал
  debug-оверлей.
- **Параметр горячий:** модуль опрашивает `/custom-config` раз в 5 с,
  как `cacheKeepalive*`, поэтому выбор в окне настроек виден сразу.
  Ключ обязан быть и в `HOT_KEYS` сервера — иначе тот сочтёт правку
  холодной и перезапустится зря.
- **safeMode гасит его через `MODULE_CHOICES`**, а не `MODULE_FLAGS`:
  выключатель строковый, и `False` модуль истолковал бы по-своему.
  Значение «выключено» здесь — `"mode"`, то есть поведение расширения
  без нашего участия.

Стенд — `node tmp/input-ring-test.js`: вырезает из живого файла оба
блока, MOOD GAUGE и INPUT RING, и гоняет их вместе на фейковом DOM.
Именно связка и хрупка: фейковый индикатор проверял бы стенд сам
с собой, а границы секторов задаёт `level()`.

## Сигнал сброса 5-часового лимита (этап 66)

Звук `.claude/notification.mp3` в момент, когда окно «5 ч» лимита
claude.ai сбрасывается на 0% — «лимит, в который упёрлись, снова
доступен», а НЕ при исчерпании. Монитор — daemon-поток
`limit_alert.py`, крутится в http-server рядом с наблюдателем конфига;
звук играет `ffplay -nodisp -autoexit`. Параметры `limitResetAlert*`
в TOML (режим any/threshold, порог процента, период опроса, повторы,
обрезка звука) — все горячие.

**Данные — сырые, не из `anthropic_usage()`.** Для полосок Accs она
маскирует истёкшее окно (`percent: 0, resetsInSec: None`) — панели так
правильно, но монитору нужны именно «процент, который был до сброса»
и «абсолютный момент сброса». Поэтому `anthropic_usage_raw()`
(account_switcher.py) отдаёт окно `five_hour` как есть; общая вычитка
`~/.claude.json` и сверка `accountUuid` живут в `_read_usage_cache()`,
общем для обеих функций.

**Момент сброса абсолютен — сигнал работает по замёрзшему кэшу.**
CLI обновляет кэш только на OAuth-логине; на провайдере и при простое
он замерзает, но `resets_at` в нём всё равно называет, докуда окно
жило. Монитор просто сравнивает его со своими часами; свежесть
(`ageSec`) для сигнала не проверяется — кэш, замёрзший перед сбросом,
по определению старый.

**Правило свидетеля.** Звук звучит только для окна, которое монитор
сам видел активным (`state.window.resetAt == resetAt`). Без него
рестарт сервера (а он перезапускается по mtime на каждую правку
исходников) на замёрзшем кэше с давно истёкшим `resets_at` играл бы
звук о сбросе, случившемся часы назад. Цена правила: рестарт,
случившийся ПОСЛЕ сброса, пропускает сигнал этого окна — принято,
состояние на диск не пишется. `decide()` при no-witness не ставит
`lastSignaledReset`, чтобы не заглушить честный сигнал, когда кэш
обновится.

- **Заполненность окна — максимум процента в рамках одного
  `resetAt`** (`percentMax`): utilization к концу окна может упасть,
  когда старая трата выпадает из скользящих 5 часов, а «упирался ли»
  выражает высшая точка. На новом окне счёт начинается заново —
  перенос максимума сигналил бы каждому следующему окну по чужой
  вине.
- **Сторонний провайдер активен — сигнал звучит, повторы гаснут.**
  Прецедент (2026-09-04): первое правило было «провайдер → полная
  тишина» («окно не тратится, сигнал — рассказ о чужой паузе»), и
  монитор промолчал при сбросе окна, заполненного на 100%, — а
  пользователь ждал именно его, работая на провайдере: упёрся →
  переключился → ждёшь звука, чтобы вернуться. Это и есть главный
  сценарий, гасить его нельзя. Пауза к тому же не давала накопиться
  свидетелю — сигнал стал бы невозможен в принципе. Что гасим
  насовсем: повторы (`allowRepeat` от `active_account_is_oauth()` в
  цикле `run_monitor`, не в `decide` — это условие работы автомата):
  кэш claude.ai на провайдере не обновится никогда, и «окно свободно»
  не сменится на «тратится» само — повтор звучал бы вечно.
- **`limit_alert.py` читает TOML сам**, как `hook_log` (путь от
  `__file__`, свежий `tomllib.load`, битый файл → «выключено»), и
  логируется через `hook_log.log("limit-alert", …)`. Импорт из
  http-server был бы циклом: сервер импортирует limit_alert ради
  старта потока. Дефолт в коде — «выключено»: битый TOML не имеет
  права включать звук сам.
- **Ключи `limitResetAlert*` обязаны быть в `HOT_KEYS` http-server:**
  правка параметра в окне настроек перезапуском сервера стирала бы
  окно-свидетель. Вписан и в `SOURCE_FILES` — в обоих местах
  (http-server.py и `_server_sources_mtime()` патчера), где списки
  обязаны совпадать.
- **Один слот плеера** под `threading.Lock`: живой ffplay глушится
  перед новым запуском (`terminate → wait(2) → kill`), звуки не
  накладываются. `Popen` с `DEVNULL` — ffplay и при `-loglevel quiet`
  пишет в stderr ругань ALSA. Закончившийся процесс подбирается
  `reap_if_done()` на каждом цикле: `poll()` и есть `waitpid(WNOHANG)`
  — без этого defunct висел до следующего сигнала (поймано на
  проверке: ручной `pkill` оставил зомби).
- **Повторы** (`limitResetAlertRepeatMin > 0`) прекращаются сами,
  когда кэш обновится новым активным окном (возобновилась работа на
  OAuth). На провайдере повторов нет вовсе — кэш там не обновится
  никогда.
- **Endpoints**: `GET /limit-reset-alert` — состояние (снимок, окно,
  последний сигнал, поле playing, наличие плеера и mp3); `POST
  /limit-reset-alert-test` — немедленный звук для проверки руками:
  реальный сброс ждать пять часов нельзя; `POST
  /limit-reset-alert-stop` — погасить играющий звук (кнопка «Стоп»).

**Кнопка «Стоп» над панелью ввода (этап 67).** Модуль LIMIT ALERT
STOP BUTTON в claude-custom.js: плавающая круглая плашка с иконкой
«стоп», висит по центру НАД панелью ввода, пока поле `playing`
истинно (опрос статуса раз в секунду), и исчезает сама, когда звук
закончился или остановлен. Клик — `POST /limit-reset-alert-stop` и
внеочередной опрос: плашка уходит сразу, а не через секунду.
Появляется по состоянию, а не живёт постоянно: останавливать нечего
почти всегда, и TOML-ключа модулю не нужно — он ничего не делает,
пока не сыграет звук, который и так включает `limitResetAlert`.
Позицию (bottom/left) считает JS по самому нижнему видимому
контейнеру поля ввода и пересчитывает при пересоздании панели и
ресайзе; центрирование — постоянный `translateX(-50%)` в CSS:
`left` задаёт ЦЕНТР плашки, и тот же transform обязан повторяться
в `:active`, иначе нажатие скинуло бы плашку на полширины. Стили —
`.claude-limit-stop-float` в claude-custom.css (палитра панелей
Accs), сама плашка — `position: fixed` в body, как панель Accs.
Три промаха опроса подряд считаются «не играет»: молчащий сервер
звуком не управляет, плашка убирается, а не висит мёртвой.

**Звуковая сцена (этап 69): громкость и чужие потоки.** На время
сигнала `duck()` глушит чужие аудио-потоки и поднимает системную
громкость до `limitResetAlertMinVolume` (0 — не трогать); параметры
`limitResetAlertDuckOthers`/`limitResetAlertMinVolume` — горячие.
Единственный контроллер аудио — `wpctl` (WirePlumber), pactl в
системе нет; всё толерантно: нет wpctl или странный вывод — сцена
не трогается, сигнал играет поверх. Мьют ≠ пауза: чужое видео
продолжает идти без звука. Возврат — тремя путями: конец звука
(`_restore_scene` из `_stop_player`/`reap_if_done`), кнопка «Стоп»
(тот же `_stop_player`) и заявка-файл
`hooks-runtime/limit-alert-restore.json`, которую подбирает
`recover_orphaned()` на старте монитора — иначе чужая музыка
осталась бы замученной навсегда после смерти сервера. Заявка
проверяет pid: живой соседний http-server со своей сценой — не трогаем;
pid после execv сохраняется, поэтому заявка прежней жизни того же pid
считается брошенной. Парсеры `parse_wpctl_volume`/`parse_wpctl_streams`
— чистые и покрыты стендом. В Streams блока Audio вперемешку лежат
воспроизведение (`Stream/Output/Audio`) и захват monitor
(`Stream/Input/Audio`, например gnome-remote-desktop). Глушить можно
только родительские узлы, у которых есть дочерний канал
`output_* > ...:playback_*`; capture-каналы `input_* < ...:monitor_*`,
Sinks и Clients не попадают. Прецедент: глушение всех главных строк
Streams убирало не только Firefox/VLC, но и само уведомление. Свой
ffplay стартует ПОСЛЕ глушения и дополнительно отфильтрован по имени.

Стенд — `python3 tmp/limit-alert-test.py`: кормит `decide()` (она
чистая, время приходит аргументом) фиктивными снимками и парсеры
wpctl живым форматом — 39 проверок на все переходы состояний.
Правишь автомат — прогоняй стенд: в живом
сервере то же самое стоит перезапуска сервера на каждую догадку.
Кнопка проверяется своим стендом — `node tmp/limit-stop-button-test.js`
(19 проверок: появление/уход, позиция и её пересчёт, единственность,
промахи сервера, метка __claudeOwnNode).

## Наблюдение за DOM: один наблюдатель на всех (этап 59)

**Модуль не заводит собственный `MutationObserver`.** Он регистрирует
функцию скана:

```js
window.__claudeDomWatch.register('mood', scan);
```

Регистрация даёт и вызовы по мутациям (с общим throttle 200 мс), и
периодический обход-подстраховку раз в 3 с, и первый скан сразу.
Собственные `observer` и `setInterval(scan, …)` в модулях запрещены —
их там больше нет ни одного.

Правило родилось из трёх отказов подряд (последний — 2026-09-02):
содержимое вкладки появлялось через 30–40 с после `Reload Window`,
поле ввода моргало по контуру и не принимало ввод, потом всё
проходило само. Бандл был цел, наш JS исполнялся, в журнале ни одного
исключения. Молчание датчика пустой вкладки само оказалось уликой:
его `setTimeout(12000)` исполнился с опозданием, когда рисовать уже
было что. Главный поток был **занят**, а не сломан.

Занят он был нами. К этапу 58 наблюдателей на `document.body` с
`subtree: true` стало семь, и throttle стоял ровно у одного —
у FIND IN PAGE, где его поставили после того, как скан на каждую
мутацию однажды подвесил webview. Стриминг ответа даёт тысячи мутаций
в секунду, браузер вызывает каждый обработчик отдельно, каждый
обходит документ целиком: работа растёт как «мутации × модули ×
размер переписки», и почти вся бесполезна — между двумя соседними
мутациями футер не меняется.

Что важно и легко сломать правкой:

- **Регистратор публикуется первой строкой блока**, до всей настройки
  ниже. Модули зовут его из своих `init()`, и отсутствие объекта дало
  бы `TypeError`, а инлайн-JS обёрнут общим `try/catch` bootstrap —
  одно такое исключение оборвало бы установку **всех** последующих
  модулей.
- **`observe` откладывается до `DOMContentLoaded`, если `body` ещё
  нет.** Блок исполняется сразу при загрузке файла (модули на него
  рассчитывают), а `observe(null)` бросает исключение молча, внутри
  `catch`, оставляя подписчиков без наблюдателя вообще.
- **Реентерабельности нет.** Сканы вставляют узлы, вставка рождает
  мутации, мутации будят наблюдателя. Цикл «скан → мутация → скан»
  уже подвешивал окно; пока идёт проход, новый не начинается.
- **Падение одного скана не лишает вызова остальных** — каждый в своём
  `try/catch`, и о падении сообщается один раз, а не на каждой мутации.
- **Предохранитель.** Скан, съевший больше 4 с за минуту, отключается
  насовсем с записью `scan-guard` в журнал. Кнопка исчезнет при
  ближайшем ре-рендере — но это лучше подвешенного окна, а запись
  назовёт виновника без дознания.
- **`characterData` у общего наблюдателя выключен**: модули следят за
  появлением и порядком узлов, а не за текстом внутри них.

**У базового модуля наблюдатель свой, и `characterData` там остаётся
включённым.** Соблазн убрать его велик — это самый шумный источник, —
но именно им виден стриминг текста ответа: без него детектор тишины
считал бы поток данных паузой и 📡 загорался бы посреди работающего
ответа. Обработчик поэтому разделён: синхронно на каждую мутацию
остаётся только отметка времени последней чужой мутации (на ней
держится детектор тишины, и throttle врал бы про возраст данных), а
всё, что обходит дерево — покраска меток 📬 и разбор мутаций для
locale-drift, — уходит под throttle 250 мс.

**Свои узлы помечаются `__claudeOwnNode = true`** и мутациями не
считаются. Оверлей живёт в том же `body`, и раньше его записи и
обновляли отметку времени последней активности, и запускали обход
дерева: патч будил сам себя. Проверка идёт по свойству, а не через
`contains` — она стоит одно сравнение на запись, а записей в шторме
тысячи. Новый наш элемент, в который что-то пишется в цикле, обязан
получить эту метку.

**Debug-оверлей не пишет вхолостую.** Он тикает каждые 100 мс, а
присваивание `textContent` мутирует дерево независимо от того,
изменился текст или нет — получалось десять мутаций в секунду, каждая
будила всех наблюдателей. Теперь скрытому текстовому блоку не пишем
вовсе, а видимому — только при изменении строки. Вычисления выше
трогать нельзя: из них берутся `busyState` и `contentSilenceSec` для
авто-пинга и 📡.

### Прибор нагрузки (`perfProbe`)

Блок PERF PROBE в `claude-custom.js` раз в 10 с сводит: **лаг
секундного таймера** (насколько занят главный поток — единственный
показатель, не зависящий от нашего кода), **время в наших
обработчиках** с разбивкой по именам (`base-observer`, `overlay-tick`,
`scan:<модуль>`, …), счётчики мутаций и **размер DOM**. Отчёт уходит
в `hooks-runtime/webview-errors.log` с `kind: "perf"`.

Читается он так: большой лаг при крошечном `ours_ms` означает, что
виноват не патч; большой `ours_ms` сразу называет модуль. `dom.nodes`
и `dom.paragraphs` показывают, виртуализирует ли расширение список
сообщений, — от этого зависит цена любого `querySelectorAll` по
документу.

Отчёт идёт своим `fetch`, а не через `claudeReportError`: у того лимит
в 20 отправок на страницу, и регулярные сводки съели бы квоту, оставив
настоящее исключение без канала. Молчит, пока всё в порядке (пороги —
150 мс на 10 с и 500 мс лага), иначе журнал заполнился бы ровными
строками «всё хорошо». Первый отчёт отправляется всегда: это baseline.

**`safeMode` прибор не гасит**, как и датчик пустой вкладки: в
безопасный режим уходят при поломке, и остаться там без измерений —
ровно та ситуация, из которой прибор родился.

### Сканы просыпаются не на всякую мутацию (этап 60)

Первый же замер прибором показал, что одного общего наблюдателя мало.
В покое приложение мутирует DOM непрерывно — 20–30 записей в секунду,
— и throttle честно пропускал по пять проходов в секунду. Каждый
проход это восемь обходов документа, а **список сообщений расширение
не виртуализирует**: 13 000 узлов на 233 сообщения лежат в DOM
одновременно. Выходило 580–746 мс на каждые 10 с, то есть 6–7.5%
главного потока — ради футера, который всё это время не менялся.

Две правки, обе в блоке DOM WATCH:

- **Фильтр релевантности.** Наблюдатель сначала смотрит, касается ли
  мутация узлов, ради которых сканы существуют (`RELEVANT` —
  `inputContainer_`, `inputFooter_`, `sessionItem_`). Отсеивается 94%
  пачек. Отдельная ветка нужна для монтирования самого контейнера:
  React вставляет поле ввода целиком, цель мутации при этом — будущий
  родитель, а контейнер лежит в `addedNodes`.
- **Один обход на проход.** Общий наблюдатель ищет узлы сам и
  передаёт их сканам аргументом `ctx`. Раньше восемь модулей искали
  одно и то же одним и тем же селектором.

Стало 65–74 мс на 10 с (0.7%), вызовов каждого скана 4–7 вместо 49.
Прибор в покое молчит — пороги не превышаются.

**Новый модуль обязан выполнить оба условия:** принимать `ctx` как
необязательный аргумент (`var containers = (ctx && ctx.inputs) ||
document.querySelectorAll(…)` — вне прохода контекста нет) и держать
свой якорный класс в `RELEVANT`. Забыть второе — значит получить
кнопку, которая появляется только с обходом-подстраховкой, то есть
через секунды после открытия вкладки.

**Промах фильтра откладывает кнопку, а не теряет её** — полный обход
раз в 3 с остался именно этой страховкой. Поэтому фильтр можно
держать строгим.

**Побочный, но важный вывод замера:** лаг таймера при загрузке вкладки
— 3.0–3.4 с при нашем вкладе 65 мс за тот же интервал. Задержка
отрисовки, с которой начался разбор, в основном **не наша**: столько
стоит расширению нарисовать невиртуализированный список. Патч её
усугублял, но не создавал.

## Пункт «⚙ Настройки» в контекстном меню и окно настроек (этап 64)

По правой кнопке на странице VSCode показывает своё меню
(Cut/Copy/Paste). **Рисует его оболочка, а не страница** — дописать
туда пункт из инжектированного JS нельзя в принципе. Проверено:
найденные в бандле строки Cut/Copy/Paste принадлежат Monaco
(`EditorContext`), а меню появляется где угодно на странице.

Штатный путь ровно один, и он растянут на четыре файла:

1. **Манифест расширения** (`patch-extension-settings.py`) — команда
   `claudeCustom.openSettings` и пункт в разделе `webview/context`.
   Пишется в `package.json` **и** в `package.json.original`: иначе
   `localize.py`, восстанавливая манифест из бэкапа, сотрёт вклад.
2. **Страница** (`claude-custom.js`) — атрибут `data-vscode-context`
   на `<body>`. VSCode при клике идёт от узла под курсором вверх и
   собирает эти атрибуты; значение `webviewSection` обязано совпадать
   с `when` в манифесте.
3. **`extension.js`** (`patch-extension-csp.py`) — обработчик команды.
4. **Окно** (модуль SETTINGS PANEL) — показывается по сообщению.

Что здесь легко сломать правкой:

- **Шестерёнка — часть заголовка, а не иконка.** Контекстные меню
  VSCode иконок команд не рисуют вовсе, поле `icon` в манифесте тут
  бесполезно. Группа `z_claude@1` ставит пункт последним: группы
  сортируются по имени.
- **Заголовок команды пишется в оба файла уже переведённым**, в
  отличие от пункта настроек рядом. Тот переводит `localize.py` по
  словарю `static.settings`; нашей строки в словаре нет, и английский
  вариант в `.original` вернулся бы английским пунктом после первого
  же восстановления.
- **Мостик команда→окно — `postMessage`, а не файл-заявка.** Файл, как
  у перезапуска хоста, пришлось бы опрашивать, а меню должно
  отзываться сразу. Ключ сообщения свой (`__claudeCustom`), чтобы не
  пересечься с протоколом приложения.
- **Кому слать, решает `panel.active`**: правый клик всегда происходит
  в активной панели. Реестр панелей пополняют те же обёртки
  `createWebviewPanel`/`deserializeWebviewPanel`, что вели журнал;
  мёртвые снимаются по `onDidDispose` — обращение к disposed-панели
  бросает исключение.
- **Команда прячется из палитры** (`commandPalette` с `when: false`):
  вне контекстного меню она бессмысленна.

### Правка конфига из окна

Окно правит `claude-custom-config.toml` — тот же файл, что и рука.

- **Запись построчная, а не через сериализатор TOML.** Файл — это
  документация: над каждым параметром абзац о том, зачем он и что
  сломается без него, и часть абзацев написана по следам поломок.
  `tomllib` комментарии не хранит, и перезапись через разбор стёрла бы
  весь текст первой же правкой. Меняется только правая часть строки
  `ключ = значение`; проверено, что запись тех же значений даёт файл
  байт в байт, а правка одного параметра — diff в одну строку.
- **Результат прогоняется через `tomllib` до записи**: сломанный
  конфиг оставил бы webview без настроек до ручной починки.
- **Неизвестные ключи отклоняются, а не дописываются в конец.** Файл
  разбит на разделы с объяснениями, ключ без абзаца выпал бы из строя,
  а сам такой ключ — почти наверняка опечатка или устаревшее окно.
- **Подсказки в окне — те самые комментарии** (`GET /config-schema`).
  Описывать флаги второй раз в JS значило бы завести два расходящихся
  источника правды. Endpoint отдельный, а не поле в `/custom-config`:
  тот опрашивают несколько окон раз в несколько секунд ради значений.
- **Что попадает в окно, решает тип, а не список** — скаляры верхнего
  уровня, как и в форме настроек аккаунта: новый флаг появится сам.
- **Перечень значений строкового параметра задаётся в его же
  комментарии** строкой `Варианты: a | b` — панель рисует по ней
  список вместо поля ввода, а сервер отклоняет запись значения вне
  перечня. Список рядом с объяснением по той же причине, что и
  разделы: человеку, читающему TOML руками, варианты видны там же,
  где смысл параметра. Разделитель `|`, а не запятая: запятая в
  обычном тексте комментария встречается, черта — нет.
  Значение из файла попадает в список, даже если его там нет:
  показать его как первый вариант значило бы соврать про файл (та же
  ловушка, что с `effortLevel: "max"` в настройках аккаунта). Отказ
  на запись нужен потому, что модуль не понял бы такое значение и
  молча откатился на своё поведение — настройка выглядела бы
  заданной, ничего не делая.
- **У модуля нет своего выключателя.** Выключив его, пользователь
  остался бы без единственного окна, из которого флаги включаются
  обратно.

## Редактор прикреплённых изображений

Модуль **IMAGE ANNOTATION EDITOR** в `claude-custom.js` добавляет кнопку
`✎` в левый верхний угол штатного полноразмерного preview изображения,
прикреплённого к composer. На самой миниатюре кнопки нет: сначала нужно
открыть изображение обычным кликом.
Включается параметром `imageAnnotationEditor` в
`claude-custom-config.toml`. Редактор работает внутри webview через
Canvas: выбор/перемещение, кисть, линия, прямоугольник, эллипс, палитра,
толщина, масштаб 25–400%, undo/redo, отмена и сохранение. Масштаб есть и
в штатном preview: кнопки `− / процент / +`, колесо мыши и pinch-жест
работают в обоих окнах; нажатие на процент возвращает 100%.

**Сохранение заменяет вложение, а не файл на диске.** Canvas экспортирует
PNG, новый `File` передаётся штатному обработчику вставки Claude Code.
Исходная миниатюра удаляется только после появления новой; при таймауте
или ошибке она остаётся на месте. Это обязательный порядок — удаление до
подтверждения потеряло бы единственную копию вложения.

Что важно при правках:

- модуль не заводит свой `MutationObserver`, а регистрирует скан как
  `window.__claudeDomWatch.register('image-annotation', scan)`;
- `buildContext()` общего наблюдателя передаёт `imageAttachments`, а
  также `imagePreviews`; селектор `RELEVANT` включает контейнер вложений,
  `pill_`, `previewOverlay_` и `previewContainer_`. Поэтому кнопка
  появляется сразу после открытия штатного preview, не дожидаясь
  резервного трёхсекундного обхода;
- контейнер штатного preview растягивается до `90vw` даже для маленькой
  картинки, поэтому класс редактора принудительно даёт ему `width:
  fit-content`: иначе ✎ и × оказываются у противоположных краёв окна;
- запуск редактора требует отдельного `pointerdown` на ✎ (либо клавиатурного
  `click` с `detail=0`). Это не позволяет тому же клику, который смонтировал
  preview, сразу открыть редактор. Перед запуском штатная кнопка закрытия
  нажимается программно, а Canvas-окно открывается в следующем task — два
  модальных слоя и их управляющие кнопки не остаются друг поверх друга;
- transform изображения не меняет layout-коробку его контейнера. Поэтому
  ✎, штатный × и панель масштаба позиционируются из фактического
  `getBoundingClientRect()` картинки после каждого изменения масштаба:
  кнопки целиком остаются снаружи верхних углов, панель — под изображением;
  когда увеличенная картинка доходит до края viewport, каждое управление
  независимо прижимается с отступом 8 px к видимой области. Снаружи
  изображения оно остаётся при наличии места, но никогда не уходит за окно;
- увеличенное за пределы viewport изображение перемещается ЛКМ. Перенос
  включается только по переполненным осям, оставляет минимум 40 px картинки
  в окне и подавляет click после реального drag, чтобы отпускание кнопки не
  закрыло preview. Управление позиционируется заново при каждом движении;
- в редакторе панель масштаба находится абсолютным слоем по центру нижнего
  footer. Статус слева и действия «Отмена/Сохранить» справа сохраняют свою
  штатную раскладку и не сдвигают центр масштаба;
- рисование хранится как векторный список действий, а не как стопка
  полноразмерных `ImageData`: undo/redo поэтому не умножает память на
  разрешение картинки;
- 100% означает исходный вписанный в доступную область размер, а не
  обязательное соответствие одного пикселя картинки одному пикселю экрана;
  при изменении размера окна редактор пересчитывает только базовое
  вписывание, сохраняя выбранный пользователем коэффициент;
- масштаб редактора меняет только экранный размер Canvas. Его внутреннее
  разрешение и координаты векторных действий остаются исходными, поэтому
  увеличение не ухудшает PNG и не меняет толщину уже нарисованных линий;
- колесо увеличивает относительно указателя, а pinch — относительно центра
  двух касаний. Начатый первым пальцем штрих отменяется, когда появляется
  второй: случайная точка от начала жеста не должна попадать в историю;
- перемещение — отдельная команда истории: инструмент `↖` выбирает
  верхний элемент под указателем, показывает пунктирную рамку и двигает
  его целиком; undo возвращает прежние координаты, redo — новые;
- большой штрих кисти выбирается как по самой линии, так и по пустому месту
  внутри пунктирной bounding-рамки. Для узкого штриха это правило не
  включается, иначе диагональная линия захватывала бы несвязанную с ней
  большую прямоугольную область;
- ПКМ временно включает тот же выбор и перенос при любом активном
  инструменте. Событие `contextmenu` на Canvas полностью подавляется,
  чтобы меню VSCode не перекрывало жест;
- рамка выбора существует только в интерфейсе: перед `toBlob()` Canvas
  перерисовывается без неё, иначе служебный пунктир попадёт в PNG;
- толщина переводится из экранных пикселей в координаты Canvas при
  начале штриха, иначе на большой картинке кисть выглядела бы тоньше;
- прямой доступ к React-state вложений не используется. Основной мост —
  `ClipboardEvent` с `DataTransfer`, запасной — штатный скрытый file
  input. После обновления расширения живым тестом проверять оба пути;
- `safeMode` обязан гасить модуль через `MODULE_FLAGS`;
- стенд: `node tmp/image-annotation-test.js`; общий контракт наблюдателя
  дополнительно проверяет `node tmp/domwatch-test.js`.

## Папка `tmp/` — вспомогательные файлы проекта

**Всё вспомогательное складывается в `tmp/` в корне проекта**, а не
рядом с рабочими файлами: стенды, черновики, разовые скрипты, выгрузки
для разбора. В `.claude/patches/` остаётся только то, что реально
уезжает в webview — `claude-custom.js`, `claude-custom.css`,
`claude-custom-config.toml`, `locales/`. Иначе каталог патчей
перемешивает то, что работает в окне, с тем, что помогало это
отладить, и при беглом взгляде непонятно, что из него можно трогать.

**Именно в корне, а не внутри `.claude/`.** На путь `.claude/` у
harness встроенная защита, которую не снимают ни `permissions.allow`,
ни bypass-режим: каждая правка файла там — отдельное окно
подтверждения. Для каталога, куда пишут по десятку раз за разбор, это
неприемлемо. Второй довод — время жизни: `tmp/` в проекте переживает
перезагрузку ПК, в отличие от системного `/tmp`, и разовый скрипт,
написанный вчера, назавтра ещё на месте. Чистится вручную, когда
надоест.

Что здесь сейчас: `domwatch-test.js`, `quote-timing-test.js` и
`input-ring-test.js` (стенды модулей, запускаются `node`),
`usage-text-picker.html` и `usage-readability-variants.html` (стенды
подбора цвета).

**Папка отслеживается git, несмотря на имя.** Стенды — не мусор:
на них держится проверка модулей, которые иначе проверяются только
через `Reload Window`, и они уже дважды ловили поломку контракта.
Класть их в `.gitignore` значило бы потерять их при клоне и получить
модули без единой проверки.

**Путь к исходнику стенды выводят от себя** (`__dirname`), а не пишут
абсолютным. Проект уже переезжал (на NVMe), и зашитый путь пережил бы
переезд молча: стенд читал бы старую копию файла либо падал.

## Destructive git-операции (обязательно)

Перед любой git-командой, которая переписывает working tree:
- `git reset --hard <commit>`
- `git checkout -- <path>` / `git checkout .`
- `git restore <path>` / `git restore .`
- `git clean -f` / `git clean -fd`
- `git stash drop` без предварительной проверки содержимого

…ты обязан **сначала**:

1. Выполнить `git status` и прочитать вывод полностью.
2. Если есть файлы со статусом `M` (modified), `A` (added),
   `D` (deleted) или `??` (untracked) — они исчезнут после destructive
   операции. До её запуска:
   - закоммить нужные правки (`git add <конкретные пути> && git commit`),
   - либо `git stash push -u -m "<описание>"` если правки нужны
     временно,
   - либо явно сообщить пользователю «после <команды> пропадут
     следующие файлы/изменения: …» и **дождаться подтверждения**.
3. Только после этого выполнять destructive операцию.

Не предполагать, что working tree чистое — всегда проверять `git status`
явно. Особенно важно, когда destructive команда — это «откат к
последнему хорошему коммиту», потому что в этот момент в WT часто как
раз и лежат недокоммиченные правки, которые ты хочешь сохранить.

Прецедент (2026-05-16): `git reset --hard cc36f09` без проверки status
снёс несохранённые правки в `claude-custom-config.toml` и
`http-server.py` — пропали локализация, debug-overlay, endpoint
`/models-list`. Восстановили только благодаря случайному бэкапу
в `.claude_old/`; в общем случае такие данные теряются безвозвратно.
